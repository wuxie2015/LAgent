# Sub-Agent 自主委派设计规划

- 日期：2026-10-30（Asia/Tokyo）
- 状态：设计规划，尚未实施。
- 目标：由主 Agent 自主判断是否启动子 Agent，将大量阅读、搜索和中间分析留在独立上下文中，减少主 Agent 的上下文占用。

## 1. 设计原则

采用“主 Agent 自主委派 + 子 Agent 独立上下文 + 有限长度结果回传”。主 Agent 负责理解用户目标、拆分任务、核验关键结果和整合回答；子 Agent 完成范围明确的调查、阅读或分析。

减少主上下文不等于减少总 Token 或耗时。子 Agent 的推理、输入和结果整合也有成本，应通过对比验证收益。已经进入主上下文的历史仍需记忆压缩处理，委派主要减少后续中间过程的积累。

## 2. 委派入口与自主选择

新增模型可调用的 `delegate_task` 工具，参数包含：

- `goal`：子任务目标。
- `context`：必要背景、相关路径、约束和权限边界。
- `expected_output`：交付格式和验收条件。

主模型在正常工具选择中自行决定是否委派，不额外增加专门判断是否委派的模型请求。第一版同步等待结果，结果返回后继续主执行循环。

| 场景 | 默认选择 |
| --- | --- |
| 简单问答、一次搜索、读取小文件 | 主 Agent 直接处理 |
| 大量材料阅读，最终仅需少量结论 | 委派 |
| 目标明确、可独立验收的调查或分析 | 委派 |
| 高度依赖完整对话、交接成本较高 | 主 Agent 处理 |
| 多个独立调查方向 | 在预算允许时分别委派；并发作为后续能力 |

提示词提供判断原则，程序控制硬性上限，不能仅依赖模型自律。

## 3. 上下文与记忆隔离

执行流程：

```text
用户目标
  → 主 Agent 理解目标、拆分任务
  → delegate_task
      → 创建独立子 Agent
      → 阅读、搜索、分析并保存独立过程
      → 返回精简结论、证据和未完成事项
  → 主 Agent 核验并整合回答
```

子 Agent 仅接收目标、验收条件、必要背景、用户及项目约束、工具权限和预算。不默认复制完整主对话，也不将子 Agent 完整消息和工具输出写入主对话。

子 Agent 使用独立内存对象和过程记录，不共写主 Agent 记忆文件。长期事实和任务状态由主 Agent 确认后统一更新，避免并发污染或把未经核验的推断作为事实保存。

完整过程记录与主上下文分离；主 Agent 必要时按引用读取相关片段，不一次性加载全部内容。

## 4. 结构化结果协议

建议结果结构：

```json
{
  "status": "completed",
  "summary": "关键结论",
  "findings": [
    {
      "claim": "发现",
      "evidence": "文件路径、行号或来源 URL"
    }
  ],
  "artifacts": [],
  "unresolved": [],
  "details_ref": "完整过程记录的位置"
}
```

状态至少区分 `completed`、`partial`、`failed`。初始返回预算建议为 2000～4000 字符，优先保留结论、关键证据、失败与限制。结果超限或格式不合规时，由程序明确处理并保留可追溯记录，不能静默裁掉失败信息后宣称完成。

主 Agent 应把子 Agent 结果视为待核验的任务产物；关键结论依据来源或文件证据确认，不能仅凭子 Agent 的完成状态宣称用户目标已经实现。

## 5. 执行预算与失败处理

建议第一版初始限制（后续依据实测调整）：

- 每次用户请求最多启动 2 个子 Agent。
- 子 Agent 不得继续创建子 Agent，最大委派深度为 1。
- 每个子 Agent 最多 4～6 轮模型调用。
- 限制子任务总耗时、输入长度和返回长度。
- 主、子 Agent 共同消耗请求级预算，子预算不能绕过全局限制。
- 为主 Agent 整合结果和最终回答预留预算。

达到预算、执行异常或结果不足时，返回明确的部分完成或失败状态、已获得证据与剩余事项。主 Agent 根据剩余预算选择自行补充、缩小目标或说明限制，避免无条件重复委派。

实现总耗时时需覆盖每轮模型调用和工具执行；仅设置外层线程等待超时不等于底层任务已经停止，不应在旧任务仍运行时盲目重试。

## 6. 第一版工具与权限范围

优先支持只读任务：资料搜索、代码阅读、日志分析和方案比较。主 Agent 负责实际文件修改，减少多个执行者同时写文件的冲突。

现有 Shell 能执行任意命令，提示词中的“只读”不能形成权限隔离。第一版应给子 Agent 配置受限文件读取、文件搜索及网页搜索工具；若直接提供现有 Shell，必须明确其不具备只读隔离，不能宣称权限已经受限。

后续支持子 Agent 写入时，再引入文件范围约束、独立工作区或写入串行化，以及变更核验机制。子任务不得获得超出用户授权的权限。

## 7. 现有架构衔接与文件规划

当前 `Agent.ask()` 已有模型与工具执行循环，可在现有工具协议上扩展委派能力，不必立即引入复杂调度框架。

| 位置 | 计划内容 |
| --- | --- |
| `src/application/agent.py` | 接入共享预算，区分主、子执行身份 |
| 新增 `src/application/subagent.py` | 创建子 Agent、管理状态、整理结果 |
| 新增 `src/tools/delegate_task.py` | 向主模型暴露委派工具 |
| `src/domain/` | 定义子任务请求、结果与预算契约 |
| `resource/prompt/` | 子 Agent 提示词、主 Agent 委派原则 |
| 配置模块与 CLI | 委派上限配置、启动及完成或失败事件展示 |
| 测试目录 | 上下文隔离、预算、失败回传与长度限制验证 |

检查时发现：`agent.py` 和 CLI 仍引用 `Memory`，而当前 `src/domain/memory/` 导出 `MemoryState`、`MemoryPolicy` 等接口。实施前应重新确认记忆系统实际状态与最终接口，避免在过渡接口上扩展。本次未运行测试，不据此断言完整运行状态。

事件应包含主任务与子任务标识，便于区分输出。完整子任务过程只写独立记录，CLI 进度事件不应被自动追加为主模型消息。

## 8. 实施阶段

1. 确认记忆接口与现有执行循环，确定任务及结果契约。
2. 实现同步委派、独立上下文、结果校验和全局预算，禁止嵌套委派。
3. 接入受限只读工具、主子提示词、CLI 状态与独立过程记录。
4. 使用相同任务对比上下文、调用次数、耗时与答案证据，验证收益。
5. 根据实测再考虑并发、后续追问、子任务续跑和受控文件修改。

## 9. 验收标准

- 简单任务可直接处理，复杂且可独立验收的任务可由模型自行委派。
- 子 Agent 不接收完整主历史，子任务原始消息和工具输出不进入主上下文。
- 返回结果长度受控，关键结论可追溯，失败与未完成事项不会被掩盖。
- 委派次数、深度、模型调用和总预算限制能由程序强制执行。
- 子任务失败后主 Agent 能继续处理或如实交代限制。
- 主、子记忆独立，子 Agent 无法直接更新主长期记忆。
- 相同任务开启与关闭委派时，对比主 Agent 每轮上下文字符数、总调用次数、总耗时及答案质量；接口提供 Token 用量时补充实际 Token 统计。
