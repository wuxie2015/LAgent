## 关键问题与证据

### P1：维护积压期间，长期事实滞后，已更正值仍作为当前值使用

- 第 50 轮也遗忘了第 31 轮审核人顾遥、第 37 轮 JPY 金额偏好；币种偏好还曾被记录成 completed 任务，随后被上下文过滤。
- 第 15 轮明确更正负责人为周岚；第 25 轮尚能答对；第 27、38、47、50 轮却答林澄。第 13、14 轮也曾答不知道早期代号和负责人，第 30 轮答不知道时区偏好。
- 任务维护优先处理旧的 pending；维护来源 ID 错误或事实候选错误会终止本次维护（`memory_manager.py:229–248, 300–311`）。压缩长期滞后。
- 上下文始终只取最后 10 个终结轮次（`context_builder.py:96`）。因此旧用户事实虽仍在盘上，也可能既不在本次上下文、又未完成长期提取。更正尚未提取时，旧负责人事实仍 active。第 27 轮上下文里甚至有第 25 轮 assistant 的正确摘要，模型仍选了旧长期值。
- 改进方向：失败重试应避免阻塞所有新轮次维护；当前明确更正需及时使旧值失效或标记待核实；积压时区分“未提取”与“无可用信息”，不要继续把旧 active 当确定现状。

### P1：已有任务没有可靠绑定，重复条目造成“已交付”和“未交付”并存

- 第 6、7 轮提取器为空，程序提示失败；第 8 轮才恢复建立 waiting_user。保护机制有效，但不满足稳定逐轮更新的体验目标。
- 第 32 轮实际已经生成三段式季度回顾报告，第 33 轮却说“报告正文尚未交付”，第 49、50 轮仍误报未交付。同一目标同时存在 waiting_user、in_progress、completed 的多个 task ID。
- 复核真实候选可见，模型遗漏已有 `task_id`，`apply_tasks` 只按 ID 查找，缺 ID 就创建新记录（`src/domain/memory/task.py:56, 103–105`）。提示词要求复用 ID，程序没有对明显重复或从已有任务复制出的候选提供可靠约束。
- 对项目代号做事实更正，也被建立成长期作业；普通“询问/确认”未被稳定排除。
- 改进方向：任务身份绑定应由程序与明确来源共同约束，不能完全依赖模型记住 task_id；已有目标 ID 缺失时不要静默新建；完成更新要更新原任务，并验证无残留等待任务。

### P2：意图被存入事实区，事实边界没有完整执行

- 第 5 轮只是“考虑将数据库迁移到 PostgreSQL，尚未决定，也没有执行”。最终 facts 里仍出现 `considering_database_migration_to = PostgreSQL`，kind 为 user_fact、status 为 active。
- 这不等于已经错误存为“已迁移”，后续多次回答仍能区分 SQLite 现状；但设计 7.1/7.3 明确要求意图与待办不要放入长期事实。
- `src/domain/memory/fact.py:91–95` 的来源检查只覆盖一组固定措辞，例如“打算”“计划迁移”“考虑改用”，没有覆盖本样本中的“考虑将……迁移”。模型提示词也未足以阻止候选。
- 改进方向：明确事实 schema 是否允许意图；按当前设计应拒绝或留在短期/任务，并加入本次真实失败样本回归。

### P2：提取模型反复抄入参考事实，来源校验正确拒绝，但缺少恢复能力

- 实际输出曾使用 `turn_user_1`、`turn_current` 等伪造来源；后续事实提取多次将 related_facts 的旧来源 ID 整批抄回，导致 source_turn_ids 不匹配或 evidence 不属于本批输入。
- `memory_extractor.py:31` 与 `fact.py:evidence_messages` 正确拒绝这些内容，没有把无效候选当空成功，也没有静默删掉原对话。
- 但每轮继续重试同一失败来源，无法稳定赶上当前对话。这是语义可靠性/恢复不足，不能通过放宽来源校验解决。
- 改进方向：减少给提取模型的无关参考信息；有限次数重试后隔离失败项并让后续维护推进，同时保持原始资料和待处理状态可见。

## 静态核对发现的其他偏差

1. 设计 7.2 要求相关事实先按 scope/subject/predicate 确定性选择；`memory_manager.py:161–167` 实际只按 scope 和更新时间选前半预算，未按主体/属性或当前内容匹配。附加内存内探针加入 8 条较新无关事实后，为“负责人更正”构造批次时，真正的 manager 参考事实完全落选。此探针是独立合成复现，不属于 50 轮主轨迹。
2. 设计 10.1 要求启动展示未完成任务简要状态；当前 CLI 只展示启动语和 notices，正常重启没有自动输出任务摘要。未完成任务可以进入模型上下文和通过 `/memory tasks` 查询，两者不能等同于启动展示。
3. 设计 17 提到维护错误、job_id、revision、事实合并/冲突数、独立提取耗时；当前生产记忆协调层没有对应日志。此次诊断依靠新增验收脚本另行记录请求，不意味着生产功能已补齐。
4. 设计 9.4 的裁剪先后为低相关项、工具预览、旧轮次；当前实现先移除事实和任务，再移除旧轮次，最后进一步缩短工具预览，顺序不完全一致。基础工具预览存在，但尚不能声称严格按设计优先级裁剪。
