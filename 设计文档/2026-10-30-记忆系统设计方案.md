# Lin Agent 分层记忆系统设计方案

- 文档版本：1.0
- 编写日期：2026-10-30（Asia/Tokyo）
- 状态：设计基线已实施；当前交付、验收和限制见 [实施与验收报告](2026-10-30-分层记忆系统实施与验收报告.md)。下文“当前实现”保留设计编写时的历史基线，实际运行行为以源码和实施报告为准。
- 适用范围：当前 Python CLI、Ollama 模型网关、网页搜索与 Shell 工具组成的单用户本地 Agent。
- 目标读者：项目维护者、实现者和验收者。

## 1. 设计结论

将记忆拆为三个逻辑区域：最近对话、长期事实、任务状态。三者的生命周期、可信程度、更新方式和上下文注入策略分别管理。

1. 最近对话：正常情况下保留最近 10 个已经终结的用户请求轮次，以及最多一个正在进行的轮次。
2. 长期事实：从被移出的旧轮次中提取可追溯、值得长期保留的事实，不保存自由形式的聊天摘要。
3. 任务状态：每轮及时记录正在执行的作业、已完成步骤、下一步、阻碍和等待用户的信息，不等到第 11 轮才更新。
4. 物理存储：先用单个 `memory/memory.json` 原子保存三个区域及元数据，另外归档退出窗口的原始轮次。
5. 分层：领域层定义数据和规则，应用层协调模型与存储，服务适配层读写 JSON、执行结构化提取。
6. 上下文：最近 10 轮是数量上限，不代表无限文本额度。组合上下文时还需遵守模型容量和工具输出预算。
7. 可靠性：提取、验证或写盘失败时，宁可暂时保留超过 10 轮的数据，也不静默丢弃历史。发送给模型的内容仍受容量约束。

本方案不引入向量数据库、独立记忆服务、后台守护进程或多 Agent。先建立正确、可恢复、可验证的最小持久化记忆体系。

## 2. 当前实现及问题

### 2.1 已有行为

以编写时源码为准：

| 位置 | 当前职责 |
| --- | --- |
| `src/domain/memory.py` | 管理 `messages`，从 JSON 加载并保存；系统提示词保留在内存中 |
| `src/application/agent.py` | 向消息列表追加用户输入、模型返回和工具结果；每轮发送全部列表 |
| `src/application/cli.py` | 创建持久化 Memory，绑定项目根目录 `memory/history.json` |
| `src/domain/interface.py` | 定义 ModelGateway 与 AgentTool 的 Protocol |
| `src/service/ollama.py` | 调用 Ollama `/api/chat`，非流式返回模型响应 |
| `src/common/prompt_loader.py` | 从文件加载最新系统提示词，替换东京当前日期 |

当前记忆文件是排除系统提示词后的消息数组。每次追加都会写盘，使用临时文件替换。启动时恢复全部历史，`/reset` 清空内存和已保存的消息。

### 2.2 需要解决的问题

- 消息列表不断增长，模型调用成本和上下文占用持续增加。
- 没有“用户请求轮次”实体，无法可靠地区分完整轮次、工具中间步骤和中断。
- 用户身份、项目约定等稳定事实容易淹没在旧对话中。
- 任务进度没有独立结构，重启后可能误判已完成或重复执行命令。
- 领域对象同时承担 JSON 存储职责，不利于继续扩展规则和测试。
- 当前 `max_tool_rounds = 8` 实际限制一次请求的模型循环次数，并非用户对话的 8 轮；新系统必须使用不同名称区分。
- CLI 当前会输出完整模型消息；引入长期事实后会扩大隐私暴露范围，需要调整调试显示策略。

## 3. 需求与范围

### 3.1 功能需求

| 编号 | 需求 |
| --- | --- |
| FR-01 | 以一次用户输入到终结响应为一轮，工具调用属于该轮 |
| FR-02 | 常态保留最近 10 个终结轮次；活动轮次额外保留 |
| FR-03 | 超出窗口的旧轮次必须先成功提取或明确判定无事实，再退出窗口 |
| FR-04 | 长期区仅保留事实及必要的来源、时效、冲突和删除元数据 |
| FR-05 | 维护多个任务和一个可选的当前活动任务指针 |
| FR-06 | 每轮更新任务状态，重启后展示未完成任务而不自动执行 |
| FR-07 | 构建容量受限、顺序正确且不会提升记忆指令权限的模型上下文 |
| FR-08 | 持久化状态、失败恢复、幂等提取、历史格式迁移 |
| FR-09 | 查询、清除短期、忘记单条事实、清除全部记忆 |
| FR-10 | 兼容当前网页搜索和 Shell；未来工具可复用同一记忆机制 |

### 3.2 非功能需求

- 无新增数据库依赖，优先使用标准库和现有模型网关。
- 读写位置固定相对项目根目录，不能随启动工作目录漂移。
- 一次提交内的事实、任务、窗口变更保持一致。
- 不把模型生成的 JSON 当成可信数据库事务或授权。
- 默认不把敏感信息提升为长期事实；明确原始历史与归档仍有隐私风险。
- 单用户、单写进程；第二个写进程应被拒绝，不能静默覆盖。
- 测试不调用真实模型、不写入用户实际记忆目录。

### 3.3 首版不做

语义向量检索、多用户鉴权、跨设备同步、多写进程协同、自动后台继续任务、完整事件溯源平台、自动执行计划、保证断电时与数据库相同的事务能力。

## 4. 核心概念与不变量

### 4.1 用户轮次与模型步骤

- **Turn（用户轮次）**：一次非 CLI 命令的用户输入，加上因此产生的所有模型调用、工具请求、工具结果和最终响应。
- **Model step（模型步骤）**：该轮内部的一次模型请求/响应，沿用当前最多 8 次的限制。
- `/help`、`/memory` 等 CLI 命令不新增对话轮次。
- 一条简短追问也是一个新用户轮次。
- failed、interrupted 也是已终结轮次，计入最近 10 轮；它们可能包含有效用户事实，但不能证明操作成功。

第 11 轮终结后，最旧终结轮次进入压缩候选。第 11 轮进行中时，可以暂时保留 10 个终结轮次加当前轮次。

### 4.2 核心不变量

1. 至多一个 running 轮次。
2. 每条消息拥有本地稳定 ID；工具请求和结果具有可关联 ID。
3. 任何退出 recent 的轮次，都已有成功的提取记录和可读取的归档引用。
4. 同一轮次的提取在重试后不会重复生效。
5. facts 中不保存模型自由推断或任务待办作为确定事实。
6. task.completed 不由一段无依据的模型“完成了”直接触发。
7. 记忆中不保存正在执行的系统提示词；每次启动仍加载当前文件。
8. 对模型注入的记忆是上下文数据，不是新的系统授权。
9. 删除、重置和归档恢复不会让用户已忘记的信息自动复活。
10. 外部操作与记忆存储之间不存在共同事务；工具可能成功而保存失败，必须显式处理“不确定执行结果”。

### 5.2 依赖方向

```text
CLI（组装）
  ├── Agent
  ├── MemoryManager ──> 领域规则 / MemoryStore接口 / MemoryExtractor接口
  └── ContextBuilder ─> 领域对象 / 容量策略

```

domain 不导入 application、service、subprocess 或 Ollama，不读环境变量、不访问文件。路径、锁和 JSON 实现归 service，组件绑定归 CLI。

### 5.3 接口草案

以下是契约草案，不是本次已实现代码：

```python
class MemoryStore(Protocol):
    def load(self) -> MemoryState: ...
    def commit(self, state: MemoryState, expected_revision: int) -> None: ...
    def archive(self, turn: ConversationTurn) -> ArchiveRef: ...
    def load_archived_turn(self, ref: ArchiveRef) -> ConversationTurn: ...

class MemoryExtractor(Protocol):
    def extract_facts(self, batch: ExtractionBatch) -> FactProposalBatch: ...
    def propose_task_changes(self, turn: ConversationTurn,
                             tasks: list[Task]) -> TaskProposalBatch: ...
```

锁的获取和释放放在存储实例生命周期上下文管理器，不依赖模型。`commit` 校验 revision；不匹配即拒绝覆盖。`archive` 可重复调用且不覆盖内容不同的同 ID 归档。

MemoryManager 提供 begin_turn、append_message、record_tool_start、record_tool_result、finish_turn、build_context、maintain、reset_recent、forget_fact、clear_all 等用例方法。模型候选操作先过领域规则，再由管理器提交。

## 6. 存储模型

### 6.1 顶层状态

```json
{
  "schema_version": 1,
  "revision": 12,
  "memory_epoch": "epoch_001",
  "created_at": "2026-10-30T00:00:00Z",
  "updated_at": "2026-10-30T00:10:00Z",
  "scope": {"kind": "project", "id": "project_001", "root": "/project/lin-agent"},
  "recent_turns": [],
  "facts": [],
  "tasks": [],
  "active_task_id": null,
  "compaction": {"jobs": [], "receipts": []},
  "archives": [],
  "forgotten": [],
  "maintenance": {"pending_turn_ids": [], "last_error_code": null}
}
```

时间统一保存为 UTC ISO 8601，界面显示为 JST。ID 用 UUID 等稳定不重复值，示例短 ID 只为阅读。schema_version 描述格式，revision 是状态提交序号，epoch 表示一次完整记忆空间生命周期。

memory.json 是权威状态；archive 中没有被状态引用的文件不能自动当成活跃记忆加载。第一版每次提交整体快照，接受文件大小线性增长的代价，后续再按实际规模评估 SQLite。

### 6.2 ConversationTurn

| 字段 | 含义 |
| --- | --- |
| id / sequence | 稳定 ID / 当前 epoch 内递增序号 |
| status | running、completed、failed、interrupted |
| started_at / ended_at | 生命周期时间 |
| user_message_id | 用户请求消息 ID |
| task_ids | 该轮关联的任务，可为空 |
| messages | 有序 MessageRecord 列表 |
| tool_executions | 工具执行生命周期记录 |
| final_message_id | 最终对用户可见回复；未产生则为空 |
| failure | 错误类型与经过脱敏的说明 |
| task_update_status | pending、applied、failed，用于恢复维护 |

MessageRecord 最少有 id、role、created_at、content、tool_calls、tool_call_id；可以保留实际供应商响应中的必要扩展字段，但不得把未知字段解释为可信权限。

ToolExecution 包含 execution_id、message_id、工具名称、经过适当处理的参数、started_at、ended_at、status、结果消息 ID。status 为 pending、running、succeeded、failed、unknown。

内部稳定 ID 与供应商工具调用 ID 分开保存。Ollama 当前消息对工具 ID 的要求由适配映射决定，不能为迁就内部格式向模型发送未经支持的字段。

### 6.3 Fact

```json
{
  "id": "fact_001",
  "scope_id": "project_001",
  "subject": "lin-agent",
  "predicate": "model_provider",
  "value": "Ollama",
  "kind": "project_fact",
  "status": "active",
  "source_type": "tool_observed",
  "evidence": [{"turn_id": "turn_001", "message_id": "msg_004", "excerpt": "OllamaClient"}],
  "observed_at": "2026-10-30T00:00:00Z",
  "updated_at": "2026-10-30T00:00:00Z",
  "valid_until": null,
  "supersedes": null,
  "conflict_group_id": null,
  "verification": "recheck_before_action"
}
```

- kind：user_fact、user_preference、project_fact、environment_fact。偏好是“用户明确表达过该偏好”的事实，不作为世界客观属性。
- source_type：user_asserted、tool_observed、user_confirmed；不提供 model_guessed 自动激活渠道。
- status：active、disputed、superseded。删除的事实正文不继续保存在 facts；只留必要删除标记。
- verification：stable 或 recheck_before_action。首版不依赖模型的浮点 confidence 来决定可信度。
- valid_until：明确过期时间；没有时效信息时为空，不等于永久准确。
- evidence 引用必须对应输入中的真实消息 ID；摘录只保留必要内容并经过敏感检查。

scope_id 不同的同名主体不合并。初期仅支持当前项目范围和显式 user 范围，不自动把项目内部事实传播为全局知识。

### 6.4 Task

```json
{
  "id": "task_001",
  "goal": "实现分层记忆",
  "scope_id": "project_001",
  "status": "in_progress",
  "origin_turn_id": "turn_010",
  "last_turn_id": "turn_012",
  "acceptance_criteria": ["最近对话最多10轮", "重启可恢复"],
  "steps": [
    {"id": "step_001", "description": "确认设计", "status": "completed", "evidence": []},
    {"id": "step_002", "description": "实现存储", "status": "pending", "evidence": []}
  ],
  "next_step": "实现存储接口",
  "blockers": [],
  "waiting_for": null,
  "completion_evidence": [],
  "created_at": "2026-10-30T00:00:00Z",
  "updated_at": "2026-10-30T00:10:00Z"
}
```

任务 status：in_progress、waiting_user、blocked、completed、cancelled。步骤 status：pending、in_progress、completed、failed。

验收标准来自用户目标和明确的实现约束，模型建议的额外验收条件不能扩大用户需求。纯写作任务可用产物消息作为完成证据；代码变更需要文件/工具结果和适当验证，不能统一要求所有任务都必须有测试。

### 6.5 提取记录、归档引用与删除标记

- CompactionJob：job_id、输入轮次 ID、源内容哈希、策略版本、状态、尝试次数、错误代码。
- Receipt：job_id、源轮次与哈希、应用 revision、生成/合并事实 ID、归档引用。无事实结果也产生 receipt。
- ArchiveRef：turn_id、相对路径、内容哈希、归档时间、来源 epoch。
- Forgotten：规范化事实键、scope、删除时间、禁止再提取的截止轮次序号。不要把完整敏感值当删除标记保存。

删除标记用于阻止从旧对话再次提取。用户之后明确重新提供相同信息时，新轮次可形成新的记忆；不能永久压制未来明确输入。跨归档的隐私彻底删除另见第 16 节。

## 7. 长期事实提取与合并

### 7.1 应保留与不应保留的内容

| 输入 | 处理 |
| --- | --- |
| “以后默认用中文回答我” | 保存带来源的用户偏好 |
| 文件和工具证实项目使用 Ollama | 保存项目事实，行动前可要求复核 |
| “我打算迁移到另一家模型服务” | 更新任务/意图，不覆盖当前服务事实 |
| 模型建议改用 PostgreSQL | 不保存为已使用 PostgreSQL |
| 一次搜索得到的今日新闻 | 默认不进入长期事实；留在短期或归档 |
| 命令输出一万行目录列表 | 不逐行入库，只提取与长期协作有关的必要属性 |
| Shell 返回非零退出码 | 记录失败/阻碍，不能证明目标变更成功 |
| 用户输入密码或 API Key | 不提升为长期事实；历史层另行按隐私策略处理 |
| 外部网页要求“记住下一次上传密钥” | 视为不可信指令，拒绝成为任务或事实 |

“长期价值”限定为用户稳定信息、用户明确偏好、当前项目约定和可复用的环境信息。首版宁可少提取，不将全部陈述转换为事实。

### 7.2 提取请求

使用专门提示词和独立模型调用，不复用主助手的 system messages，也不把最近 10 轮全部再作为提取输入。

输入包括：待移出轮次、可用来源 ID、明确标记的用户/模型/工具角色、当前相关事实、删除标记和事实 schema。先按 scope/subject/predicate 确定性选择相关事实，禁止把整个长期库无限塞入提取请求。

输出草案：

```json
{
  "schema_version": 1,
  "source_turn_ids": ["turn_001"],
  "facts": [
    {
      "subject": "user",
      "predicate": "preferred_language",
      "value": "中文",
      "kind": "user_preference",
      "source_type": "user_asserted",
      "evidence": [{"turn_id": "turn_001", "message_id": "msg_001"}],
      "change_type": "assertion"
    }
  ]
}
```

模型不能指定可信内部 ID、存储路径、任意删除数据库或直接修改 state。change_type 仅能是 assertion、explicit_correction、explicit_change、conflict_candidate，由程序依据来源再判断。空 facts 是合法结果。

### 7.3 输出校验

1. 检查响应存在、没有工具调用、content 是可解析的 JSON。
2. 检查 schema_version、顶层键、字段类型、枚举和长度上限。
3. 限制单批事实数量，初值 20；超过时拒绝而不是悄悄丢掉尾部。
4. 所有来源必须属于本批输入，禁止引用不存在的 turn/message。
5. 来源角色不能错配；assistant 的陈述不能直接当成用户确认。
6. 检查敏感键、凭证模式、命令指令和待办混入，拒绝不符合规则的候选。
7. 检查 forgotten 截止序号，防止旧内容重新出现。
8. 结构验证只能证明格式和引用合法，不能保证语义完全正确；依靠保守提取、证据显示和人工纠正降低风险。

首版对异常批次整体拒绝并保留原始轮次，避免半批成功造成难以追踪的行为。不能因为 JSON 无法解析就默认“没有事实”。

### 7.4 去重、冲突和更新

规范化键由 scope_id、subject、predicate 构成，规范化仅做大小写/空白等安全处理，不用宽泛相似度把不同实体强行合并。

- 相同键且值相同：合并来源、更新时间，不新增事实 ID。
- 同键不同值且有明确纠正/变更证据：旧项置 superseded，新项 active，记录 supersedes。
- 同键不同值但没有明确更新语义：两项进入 disputed 同组，不把后来的陈述直接视为真相。
- 多值属性（例如用户掌握的语言）必须在规则中明确允许集合合并，不能套用单值覆盖。
- 环境或文件状态即使被工具验证也只有“观察时成立”的含义。
- 过期或 superseded 项默认不进入活跃上下文，可用于用户主动追溯。

不进行摘要的反复摘要：提取旧原始轮次，合并结构化事实，避免每次重写所有事实造成漂移。

## 8. 任务状态管理

### 8.1 建立任务

CLI 的普通问答、翻译一句话、闲聊默认不建立持久任务。明确的创建、修改、排查、调研产物等执行请求可建立任务。自动判断不确定时先作为当前轮次处理，不强行生成持久任务。

任务可由主轮次结束后的模型候选更新建立，来源必须引用明确的用户请求；不在用户输入到达时额外强制调用模型分类。工具执行检查点仍从开始执行时记录，即使 task 尚未分配。

“继续之前的任务”只在目标明确时绑定已有 task；存在多个可能任务时询问。临时插入问答不自动取消当前活动任务。

### 8.2 状态转换

```text
in_progress → waiting_user / blocked / completed / cancelled
waiting_user → in_progress / cancelled
blocked → in_progress / cancelled
completed → in_progress（仅用户明确要求继续、返工或可靠证据证明未完成）
cancelled → in_progress（仅用户明确恢复）
```

waiting_user 表示缺少用户参数或确认；blocked 表示外部依赖、权限或服务障碍，必须写明原因。达到一次工具循环上限只能记为未完成/受限，不能自动置 completed。

完成标准与用户任务类型匹配：解释类交付可由最终消息证明，写文件由工具结果及读取验证证明，部署由相应部署和运行检查证明。工具 exit_code=0 只证明该命令正常返回，不能证明业务目标一定达成。

### 8.3 更新时机

- 主轮次进行中：程序直接写入消息、工具执行检查点和已知执行结果；不依赖额外模型请求。
- 主轮次终结后：任务提取器生成候选变更，校验后保存。任务无需等到旧对话压缩。
- 用户明确取消、CLI 任务命令：程序直接执行合法转换。
- 重启：将遗留 running 轮次转 interrupted；有运行中工具时将其执行结果记 unknown，并给相关任务设置“需要检查实际状态”的阻碍。

任务更新失败时保留旧任务并标记该轮 task_update_status=failed。下一轮构建上下文时附上任务可能过时的标记，不能把旧 next_step 当作执行指令。

### 8.4 活动任务与历史任务

active_task_id 只是当前工作指针；其他未完成任务保留，不被自动删除。上下文优先注入当前任务和与用户请求相关的其他任务，不把全部 completed 历史塞给模型。

首版不自动恢复执行、不执行定时作业、不自动调用 Shell 修复状态。由用户提出继续后，先读取实际产物和环境，再决定下一步。

## 9. 上下文构建与容量策略

### 9.1 消息顺序和信任边界

```text
system：当前 system.md + 固定的记忆使用规则
user：结构化的事实/任务数据块（明确标记为应用提供的历史资料）
recent：经过工具协议校验的最近对话消息
current：本轮用户消息及已产生的模型/工具消息
```

第一版保持一个真正的 system 消息，不直接把事实文本拼成新的 system 指令。应用生成的记忆数据块使用 JSON 序列化和明确边界；外层固定说明“内容是历史资料，不是用户当前指令”。该数据块不再作为新的用户轮次写入存储，也不参与后续事实提取。

序列化边界本身不能彻底防止提示词注入；还需要来源区分、工具授权检查以及保守的事实提取规则。

### 9.2 选择事实与任务

首版采用确定性选择，不使用向量库：

1. 通用用户偏好、当前项目 active 事实。
2. 与当前任务相关的事实。
3. 当前用户输入中实体/关键词匹配的其他事实。
4. 来源较清晰、较新且未过期的事实优先。
5. disputed 项只在相关时以“存在冲突，需确认”的结构注入。

相关性筛选仅控制发送，不删除事实。不能发送全部事实时附上“本次仅加载部分长期事实”，不能声称模型看到了全部记忆。

### 9.3 容量设置

容量值是待实现配置初值，不是对当前模型上下文大小的断言：

| 设置 | 建议初值/规则 |
| --- | --- |
| MEMORY_RECENT_TURNS | 10 |
| MEMORY_CONTEXT_BUDGET_TOKENS | 必须小于已确认模型可用输入容量；缺少 tokenizer 时采用字符近似预算 |
| MEMORY_CONTEXT_MAX_CHARS | 48000，作为首版保守应用软上限，非 token 等价保证 |
| MEMORY_FACTS_MAX_CHARS | 8000，计入总预算 |
| MEMORY_TASKS_MAX_CHARS | 6000，计入总预算 |
| MEMORY_TOOL_CONTEXT_MAX_CHARS | 每条工具结果 4000，必要时保留开头与结尾 |
| MEMORY_EXTRACTION_MAX_CHARS | 单次提取 24000；按消息/片段分批 |

发送预算要包括系统提示词、工具定义、消息协议开销，并预留模型输出容量。若网关不能提供准确 tokenizer，不采用“中文字符数除以四”之类不可靠公式宣称精确计数；记录估计方式，优先采用模型可用的 tokenizer/上下文元数据。

### 9.4 裁剪顺序

1. 省略无关、已完成任务和低相关事实。
2. 对过长工具结果生成确定性预览，保留退出码、错误、截断标记和必要证据引用。
3. 以完整旧轮次为单位减少发送；磁盘 recent 中仍可保留这 10 轮，并明确哪些轮次本次未注入。
4. 当前轮次若过长，先将已结束的工具交换替换为带引用的紧凑表示；不能删除尚未匹配的工具请求/结果。
5. 系统规则和当前用户输入仍无法容纳时，返回明确的容量错误，要求缩小输入，不偷偷截断用户要求。

“10轮完整保留”指存储和常态上下文。超出模型容量时采用上述例外，不能承诺任何长度都完整发送。模型只能依据实际提供的片段作结论。

## 10. 完整运行流程

### 10.1 启动

1. 加载项目配置和最新系统提示词。
2. 获取当前项目记忆目录的独占写锁。
3. memory.json 不存在时检查是否需要旧格式迁移，否则建立空状态。
4. 校验 schema、revision、所有引用和结构大小限制。
5. 若遇到不支持的新版本，拒绝写入，不用旧 schema 覆盖。
6. 处理 running 轮次与 unknown 工具，原子保存恢复结果。
7. 校验已引用归档，发现损坏保留状态并报告，不自动替换为空记忆。
8. 加载未完成任务的简要状态；不自动执行命令。
9. 进入 CLI 循环。维护重试放到显式请求处理边界，不在启动时无限调用模型。

### 10.2 一次用户请求

```text
用户输入
  → 建立 running 轮次并保存
  → 按预算构建上下文
  → 调用主模型
      → 最终文本：保存最终消息，轮次 completed
      → 工具调用：保存请求与执行检查点
          → 执行工具
          → 保存结果与执行状态
          → 再构建上下文并调用模型
  → 异常/中断/超限：保存对应终结状态和可见说明
  → 提取任务变更并保存
  → 超过10个终结轮次时压缩最旧轮次
  → 显示最终回答及必要的维护提示
```

主模型失败、未知工具、JSON响应不完整、KeyboardInterrupt 均需要结束轮次或明确标为 interrupted，不能留下永久 running。主回答与记忆维护错误分别报告；维护失败不改写已完成的任务回答为“执行失败”。

最终回答先持久化，再做有界维护，最后显示。首版同步执行，允许增加延迟；未来要流式提前显示时，应另行设计输出阶段和维护并发控制。

### 10.3 旧轮次压缩

```text
锁定单写状态，找出窗口外的终结轮次
  → 创建稳定 job（轮次ID + 内容哈希 + 策略版本）并保存 pending
  → 对待退出轮次调用事实提取器（无工具）
  → 校验并确定性合并候选事实
  → 写入/复用原始轮次归档，校验哈希
  → 构造新快照：facts合并 + receipt + archive引用 + 移出recent
  → revision + 1，原子提交
```

单轮过长时分片提取，保留片段来源范围；只在所有片段成功后应用整轮事务。语义跨片段可能遗漏，应优先按消息和完整工具交换边界切分。receipt 关联整轮与各片段哈希。

退出窗口前的任务更新必须 applied，或明确完成受控降级并保留待更新输入引用；首版选择前者，不在任务更新失败时移出该轮。

### 10.4 模型调用预算

主任务最多 8 个模型步骤，与记忆维护分离。维护每个用户请求最多 2 次模型调用，每次超时建议 30 秒，总维护时间预算 60 秒；是否可在单个请求里及时取消需要网关支持。

正常情况下：1 次任务候选更新；若发生窗口淘汰，再 1 次事实提取。不为两种不同输入强行共用一次模型请求，避免来源混淆。无任务相关变化、普通闲聊且无活动任务时可跳过任务提取。

维护阶段不启用主助手工具，传入 `tools=[]`；返回工具调用视为无效。现有 OllamaClient 的固定180秒请求超时需要改为可配置，使维护预算真正生效。

超过预算或有积压时，不在同一轮无限重试；记录 pending 和错误，下轮边界至多再处理一个有限批次。积压达到配置阈值（建议 30 个终结轮次）时进入显式降级：告知维护持续失败、保留磁盘内容、按容量选择模型上下文，提供 `/memory retry`，不伪称仍完整记得所有轮次。

## 11. 持久化、一致性和崩溃恢复

### 11.1 单快照提交

写入流程：验证新状态 → 在 memory.json 同目录创建权限受限的临时文件 → UTF-8 序列化 → flush → fsync 文件 → os.replace → 尽可能 fsync 父目录。

replace 必须位于同一文件系统。单快照解决 facts、tasks、recent 同时更新的一致性，不等于所有归档文件与外部命令具有数据库事务。磁盘写满、权限错误、文件系统不支持目录同步等情况必须有明确错误处理。

内存 state 只在 commit 成功后替换为新快照。不要先永久改变 live state 再发现写盘失败而继续执行。若 replace 已成功但目录同步失败，属于 durability_uncertain；停止后续写操作并重新读取校验，不能简单回滚到可能过时的内存。

### 11.2 归档顺序

先写完整归档并校验，再提交引用它的新状态：

| 崩溃位置 | 恢复行为 |
| --- | --- |
| pending job 尚未写入 | 旧 recent 完整，重新创建 job |
| pending 已写、模型尚未返回 | 旧 recent 完整，可按相同 job 重试 |
| 模型返回、合并尚未提交 | 重新提取；没有 receipt 就不认为已生效 |
| 归档写入、新快照未提交 | 归档是孤立副本，recent 仍权威；重试按哈希复用 |
| 新快照已提交 | receipt 和 archive 引用有效，不重复应用 |
| 新快照损坏 | 报错并保留现场，不自动使用孤立归档重建“新事实” |

对孤立归档只提供诊断和显式清理，不自动注入上下文。正常清理前确认没有被当前 state、迁移或待重试 job 引用。

### 11.3 单写锁

在进程生命周期使用操作系统文件锁；文件存在不等于锁有效，不能只靠 `.lock` 文件是否存在判断。当前平台可使用标准库 `fcntl.flock`，跨平台再由适配层替换。

第二个进程给出“该项目记忆正在使用”的清晰提示并退出。revision 检查是额外防护，不能代替锁。锁文件留在磁盘不是故障，进程退出后操作系统锁应释放。

### 11.4 外部副作用检查点

执行 Shell 等有副作用工具之前，必须持久化 execution_id、命令参数和 running 状态；保存失败时不执行该工具。

执行之后先保存实际结果。若命令成功但保存失败：

1. 当前进程停止继续发起工具调用，向用户报告“命令可能已执行，结果未可靠写入记忆”。
2. 不自动重试该命令，即使工具名称和参数完全相同。
3. 重启后该执行标 unknown，并依据文件或外部服务实际状态恢复。
4. 多个并行工具必须各自有检查点；主循环终止不代表已经启动的工具都被取消。

检查点防止盲目重放，但无法实现 exactly-once 外部执行。只有外部系统自身支持幂等键时才能进一步增强保证。

### 11.5 错误分类

| 错误 | 策略 |
| --- | --- |
| 模型提取超时/无效JSON | 保存维护错误，保留轮次，后续有界重试 |
| 未知schema或损坏状态 | 拒绝覆盖，要求显式修复/恢复 |
| 归档缺失/哈希不匹配 | 标记完整性异常；不伪造证据，不自动删事实 |
| 写盘失败 | 暂停后续副作用操作，明确提示 |
| 主模型上下文溢出 | 按预算再构建一次；仍失败就返回容量限制 |
| 事实冲突 | disputed，不静默选一方 |
| 工具结果不确定 | task标需核查，禁止自动重放 |
| 提取连续失败 | 降级可见性和显式重试，不丢盘上数据 |

## 12. CLI 行为与兼容性

命令为拟议接口，当前项目尚未实现这些新命令。

| 命令 | 语义 |
| --- | --- |
| `/memory` | 显示轮次数、事实数、待办数、维护状态；不默认输出事实正文 |
| `/memory facts` | 查看当前scope事实及ID、来源、状态 |
| `/memory tasks` | 查看未完成任务及当前活动指针 |
| `/memory fact <id>` | 查看单条事实详情和必要证据 |
| `/memory forget <id>` | 删除活跃事实并建立截止旧轮次的删除标记 |
| `/memory retry` | 有界重试待处理任务更新/事实压缩，不执行历史Shell |
| `/task use <id>` | 选择已有未完成任务 |
| `/task cancel <id>` | 取消任务，不清除事实或历史 |
| `/reset` | 清除recent当前对话，保留facts和tasks，清空active_task_id |
| `/memory clear-all` | 经明确确认后清除全部记忆及相关归档/迁移副本 |

### 12.1 `/reset` 细节

这是与现有实现不同的语义，必须更新 `/help`、README和system.md。清除前提示“未提取的短期事实不会保留”，不为了 reset 强制发起模型请求。

reset 不把被清除轮次归档、不重新提取；取消这些轮次的维护 job。保留的 tasks 标记“对话已重置，继续前需核查”，避免模型依靠缺失对话推断授权。已有任务数据不等于重新授权。

当前同步CLI只能在本轮结束后接收命令。若未来支持运行中reset，必须先中断并确认在途工具状态；本版不承诺即时停止所有外部进程。

### 12.2 清除全部

clear-all 先显式展示清除范围，再要求确认；执行中进入 maintenance_mode，停止新任务和模型提取。创建新的 epoch 和空快照，并清理旧 epoch 的归档、临时文件和迁移备份。

若物理删除失败，新状态仍不得加载旧数据，CLI列出残留路径并报告“逻辑清除完成，物理清理未完成”。不能声称安全擦除SSD、系统备份或操作系统快照。运行日志独立说明，不默认含对话正文。

### 12.3 首版命令优先级

最小实现必须具备 `/reset`、`/memory`、`/memory facts`、`/memory tasks`、`/memory forget <id>`、`/memory clear-all`。其他命令可后续实现，但不能用提示词暗示不存在的命令已经可用。

## 13. 旧历史迁移

### 13.1 触发条件

- memory.json 存在且有效：直接用新状态，不再次导入history.json。
- memory.json 不存在、history.json 存在：执行一次显式可见的自动格式迁移。
- 两者都不存在：创建新记忆空间。
- 新状态损坏：停止；不能悄悄回退导入旧历史导致已删除信息复活。

### 13.2 迁移步骤

1. 获取独占锁，完整校验旧JSON数组及消息role。
2. 创建按时间/哈希区分的只读迁移备份，保持原文件不变直到新状态提交成功。
3. 用user消息划分轮次，system消息不导入；没有起始user的孤立工具/assistant消息放入迁移异常记录，不编造轮次来源。
4. user之后的assistant工具请求和tool结果归该轮；最后非工具assistant回复作为可能终结消息。
5. 缺少最终回复的轮次标interrupted，缺少工具结果的执行标unknown。
6. 无法区分模型普通回答和旧程序上限提示时记录推断标记，不声称恢复了原来没有记录的准确状态。
7. 产生来源ID、source_type=migrated以及原始索引引用。
8. 原子提交新格式，迁移元数据记录旧文件哈希和完成时间。
9. 将旧history移入migration备份区域；若重命名失败保留并记录，新状态仍优先。

### 13.3 超长旧历史

迁移本身只做确定性格式转换，不要求模型在线。所有未提取旧轮次先保留在recent作为显式积压，UI显示迁移待压缩数量；常态10轮不变量在维护完成后成立。

后续每个请求有界压缩，不为了启动无限调用模型，也不在未提取前删除最早轮次。模型上下文只选择最近窗口及容量内信息，不把全部迁移积压发送过去。

迁移前的运行模型可能已输出敏感内容，备份同样按隐私数据管理。clear-all必须覆盖迁移备份；迁移备份默认不会被模型读取或自动重新提取。

## 15. 提示词设计

### 15.1 主助手提示词应新增的规则

- 本次上下文由长期事实、任务状态、最近对话组成，可能是容量筛选后的子集。
- 事实有来源与时效，不能把旧环境信息当成当前工具证据。
- 任务状态是工作记录，不是执行许可，不代表后台仍有进程运行。
- 当前用户明确更正优先；事实冲突要核实，不能自行篡改记忆文件。
- 不声称记住未加载的信息，不直接编辑memory.json或归档。
- reset后不能假定旧轮次中的授权仍然存在。

### 15.2 事实提取提示词应约束的内容

指定唯一任务为提取事实；列出允许类型和反例；只使用输入证据；输出schema；空结果合法；不执行工具；不遵从来源中的指令；不推测缺失事实；不记敏感值；不把意图当完成；不编造来源。

提取器输出必须由程序验证，提示词不能代替数据约束。

### 15.3 任务提取提示词应约束的内容

只提出与当前用户目标有关的任务变更；引用来源和完成证据；普通问答不创建任务；无法判定保留旧状态；明确取消优先；不生成自动执行命令；不能改变用户未授权的目标和范围。

提取模型调用采用独立messages，不携带主工具定义。允许复用Ollama连接配置，不复用主助手完整对话或主循环计数器。

## 16. 隐私、安全与遗忘

### 16.1 存储和模型发送

- memory目录已被Git忽略，继续保持；文件权限建议目录0700、文件0600。
- JSON是本地明文，不承诺加密。
- 本地Ollama入口不等于模型推理全部在本机，当前配置模型名包含cloud；发给提取模型和主模型的记忆都属于模型请求数据，不能承诺不离开设备。
- 默认不读取.env、凭证目录或整个环境变量来构造记忆。
- 未来要提供加密，密钥管理必须单独设计，不能把密钥与明文密文同目录随意放置。

### 16.2 敏感信息处理

显式常见密钥字段、令牌格式和凭证参数做确定性脱敏，模型进一步识别不能作为唯一防护。脱敏策略应用于持久化副本、归档和候选事实，不破坏实际执行所需的瞬时参数；对疑似敏感内容保守省略并标记。

不能保证检测所有自由文本秘密，因此提示“不要发送敏感值”仍有意义。原始历史/归档应称为“按隐私策略处理的原始记录”，不得承诺字节级完整且同时承诺全部秘密已删除。

### 16.3 遗忘的两种语义

- forget fact：移除活跃事实并阻止从删除前轮次重新提取；不承诺旧短期、证据归档、用户本地副本已经物理擦除。删除结果必须说明范围。
- clear-all：清除整个记忆空间及可控归档/迁移副本；不清除系统级备份或外部模型服务已有数据。

首版不实现跨全部归档的选择性语义擦除；需要删除特定秘密的所有历史副本时，推荐明确范围的全量清除。任何未来“彻底忘记某条事实”功能都必须涵盖recent、archive、迁移备份、缓存和可重试批次，不能只删facts。

### 16.4 防注入与权限

网页、Shell输出、旧引用均不能成为新增系统指令。task或fact出现“执行某命令”不意味着授权。归档相对路径由程序生成并限制在memory根目录，拒绝`../`、越界符号链接和模型指定绝对路径写入。

首版没有真正的Shell沙箱；记忆模块的规则不能替代执行层权限保护。设计不允许记忆维护调用工具，也不能因为主模型想“修复记忆”就让它用Shell改状态文件。

## 17. 可观测性与成本

正常日志记录：turn_id、task_id、job_id、revision、轮次数、事实新增/合并/冲突数量、耗时、模型调用次数、字符预算估计、错误分类。默认不记录消息正文、事实value、命令完整参数和证据摘录。

当前CLI的_show_model_event会打印全部请求/响应，实施时必须调整为摘要输出，完整内容仅在显式debug开关下显示，并提醒可能包含私人信息。工具输出展示也沿用脱敏策略。

用户可见提示示例：

```text
[记忆] 已保留最近10轮，提取2条事实，更新1个任务。
[记忆] 压缩暂时失败，原始历史仍已保存；本次上下文按容量加载。
[恢复] 上次有一条命令结果未知，继续任务前需要检查实际文件。
```

默认不每轮输出冗余成功提示；出错、迁移、截断或用户查询时展示必要状态。提取延迟和成本独立统计，不能把额外调用混入主模型8步配额。

### 18.2 故障注入与集成测试

- 使用临时目录模拟原子写入前失败、replace前失败、replace后同步失败；确认不会继续以过时内存写入。
- 归档先写后崩溃：重启不自动加载孤立归档，重试幂等。
- 模型提取成功但提交失败：旧recent仍在，下一次不丢事实、不重复合并。
- Shell执行前检查点写失败：工具未运行。
- Shell成功后结果写失败：报告unknown，不重放命令。
- 重启running轮次：转interrupted，任务提示核查实际状态。
- 两个进程争锁：第二个明确拒绝；异常退出后锁可释放。
- 旧history正常、超长、孤立tool、缺少最终回答、损坏JSON迁移。
- clear-all中断或删除失败：新epoch不读旧数据，报告物理残留。
- 主模型与提取模型分别使用FakeModel验证工具列表、提示词隔离与调用预算。
- 所有测试不依赖真实网络或模型，且不读取用户memory正文。

## 20. 决策记录

| 决策 | 理由 | 代价/约束 |
| --- | --- | --- |
| 三类逻辑记忆 | 生命周期与可信规则不同 | 需要明确协调层 |
| 一个状态JSON | 避免三文件部分更新 | 大规模时整体重写成本高 |
| 原始轮次归档 | 支持证据追溯和提取失败恢复 | 磁盘增长、隐私成本 |
| 非向量检索首版 | 当前规模不需要额外服务 | 相关性选择能力有限 |
| 同步有界维护 | 简化一致性和单进程模型 | 回复增加维护延迟 |
| 独立任务/事实提取 | 输入范围不同、时机不同 | 常态可能增加1–2次模型调用 |
| 失败保留超额recent | 优先不丢内容 | 常态10轮需允许故障例外 |
| 工具检查点 | 避免重启盲目重放 | 无法提供外部exactly-once保证 |
| 保守事实合并 | 降低长期污染 | 需要用户处理少量冲突 |
| 清除短期与全量分离 | 兼顾连续协作和遗忘 | reset语义变化需明确告知 |

## 21. 已知限制与未来演进

- 提取语义无法被JSON验证完全证明正确，长期事实必须可查看、纠正和删除。
- 字符预算不是精确token预算，准确上限取决于实际模型和部署配置。
- facts和receipts数量仍可能增长；首版提供观测，不承诺永远无需维护。后续根据真实大小考虑SQLite、索引和历史元数据清理。
- archive首版默认保留到显式清除，不自动按天删除，以免破坏证据引用；磁盘容量需提示，配额满时停止归档/压缩并降级，不静默删数据。
- 不支持多个写入者；多个项目共用全局用户记忆需要另行设计scope、权限和冲突。
- 主循环目前同轮工具可并行，但写入类工具的依赖与权限控制应在执行层完善，记忆系统不能独立解决。
- 当前工具返回只限制输出长度，不等于限制整个轮次、执行磁盘占用或外部副作用。
- 若以后启用模型后台运行或流式响应，需要重新设计维护调度、取消传播和同一轮的并发更新。

## 22. 示例：从短期到长期再到恢复

假设第1轮用户说“这个项目以后默认中文回复”，并确认一项文件修改任务。第2–10轮是普通问答。

1. 第1–10轮终结时，recent有10轮；任务在对应轮结束后已更新，而不是等压缩。
2. 第11轮开始，recent有10个终结轮次和1个running轮次。
3. 第11轮结束，任务更新成功后，选择第1轮提取事实。
4. 提取出user_preference：preferred_language=中文；文件修改的待办保留在tasks，不作为已完成事实。
5. 写第1轮归档，提交事实、receipt、归档引用和窗口退出，recent变为第2–11轮。
6. 重启：加载当前system.md、facts、tasks和recent；没有running工具就正常进入交互。
7. 用户说“继续那个文件任务”：先从状态确定任务，再检查目标文件实际内容，避免依赖旧状态盲目修改。
8. 用户执行`/reset`：recent清空，偏好与任务保留但任务需复核；旧recent不再被自动提取。
9. 用户执行`/memory forget fact_x`：该事实退出活跃上下文，旧来源不会再次提取；命令说明归档原文仍可能存在。
10. 用户确认`/memory clear-all`：切换新epoch并清理受控副本，重新开始。

此例展示三类记忆的分工：短期用于理解连续表达，事实用于保持稳定信息，任务状态用于记录工作进度；任何一类都不能代替当前用户授权或工具对实际世界的检查。
